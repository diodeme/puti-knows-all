# 语义扩展体系设计

## 1. 文档目标

本文档用于定义 `maling-java-graph` 面向开源的语义扩展体系，重点解决以下问题：

- 如何让 Spring Boot、Quarkus、CDI 等同一 DI 元模型下的差异尽量只通过规则抹平
- 如何避免把底层解析能力和框架语义判断继续糊在单个 processor 中
- 如何让二次开发者按需求复杂度做梯度扩展，而不是一上来就理解整套内部抽象
- 如何在后续接入数据流能力时复用同一套扩展框架

本文档是 [`Java语义图谱V1开源重构任务书.md`](./Java语义图谱V1开源重构任务书.md) 的补充设计，不替代任务书的里程碑与交付定义。

---

## 2. 设计目标

扩展体系必须同时满足以下四个目标：

1. 默认简单，小需求优先只改规则
2. 框架语义差异尽量下沉到 rule pack，不污染核心流程
3. 复杂需求允许逐层下沉到函数扩展、语义 pass、事实提取
4. 后续接入数据流时，规则系统复用“解释事实并产图”的能力，而不是替代分析器

用一句话概括：

`默认简单，按需升级；代码负责求事实，规则负责解释事实。`

---

## 3. 非目标

本扩展体系不追求以下目标：

- 全配置、零代码支持所有新场景
- 用规则系统替代 AST、符号绑定、类型推断、数据流求解
- 为 V1 引入过多通用平台抽象
- 一上来暴露过多内部概念给普通用户

---

## 4. 核心判断

### 4.1 哪些差异应该落到规则

适合 rule pack 处理的，是共享同一语义元模型下的框架差异。例如：

- 哪个注解表示 provider
- 哪个注解表示 injection point
- bean name 从哪里提取
- qualifier 怎样提取和比较
- primary/default/priority 如何参与排序
- 哪些解析结果需要落图
- 哪些调用需要做 receiver retarget

这类差异本质上是“语义映射差异”，不应该继续堆到 Java 主流程里。

### 4.2 哪些能力必须保留在代码中

以下能力仍然必须由 analyzer / resolver 代码承担：

- AST 遍历
- 符号绑定
- 类型推断
- `return new ImplA()` 这类实际类型求解
- 字段、局部变量、参数与调用接收者的关联
- override / overload 解析
- 数据流传播与摘要计算

因此，正确边界不是“是否使用 rule”，而是：

`规则决定语义和落图，代码提供事实和解析基础。`

---

## 5. 分层设计

扩展体系建议固定为四层。

### 5.1 Core Analysis Layer

职责：

- 解析 Java AST
- 提取结构化事实
- 建立符号、类型、调用等基础分析结果

要求：

- 这一层不直接认 Spring、Quarkus、CDI 品牌
- 产出稳定的 typed facts

### 5.2 Semantic Resolution Layer

职责：

- 基于事实和规则做语义归并
- 形成绑定结果、调用重定向结果、摘要结果

要求：

- 这是 rule pack 的主要作用层
- 不应把框架专有 if/else 重新堆回 processor

### 5.3 Graph Mutation Layer

职责：

- 将 resolution 结果转换为 graph mutation
- 输出 edge、node property、semantic tag

### 5.4 Presentation Layer

职责：

- server / frontend 消费通用图协议
- 不感知具体规则包来自哪个框架

---

## 6. 通用事实元模型

为了让 Spring Boot 和 Quarkus 这种差异只改规则，不改核心代码，底层必须先抽出通用事实元模型。

V1 推荐至少保留以下事实。

### 6.1 ProviderCandidate

表示一个潜在 provider。

建议字段：

- `sourceId`
- `sourceKind`
- `declaredType`
- `actualType`
- `providerName`
- `qualifiers`
- `priority`
- `scope`
- `frameworkHints`

### 6.2 InjectionPoint

表示一个注入点。

建议字段：

- `ownerId`
- `memberName`
- `memberKind`
- `requiredType`
- `requestedName`
- `qualifiers`
- `required`
- `injectionMode`
- `frameworkHints`

### 6.3 CallSite

表示一个调用点。

建议字段：

- `callerId`
- `receiverSymbol`
- `declaredReceiverType`
- `methodName`
- `argumentTypes`
- `location`

### 6.4 TypeRelation

表示类型间基础关系。

建议字段：

- `sourceType`
- `targetType`
- `relationKind`

### 6.5 后续数据流预留

V1 不落数据流，但建议预留：

- `DataFlowObservation`
- `DataFlowSummary`

## 7. 两轮解析模型

为避免继续把框架逻辑塞进单个 processor，建议统一采用“两轮解析 + 一步落图”的模型。

### 7.1 第一轮：Collect Facts

目标：

- 只产出事实
- 不直接产最终框架语义边

例如在如下代码中：

```java
@Bean
public InterfaceA beanA() {
    return new ImplA();
}

@Autowired
@Qualifier("beanA")
private InterfaceA a;

a.doSomething();
```

第一轮应至少产出：

- 一个 `ProviderCandidate`
- 一个 `InjectionPoint`
- 一个 `CallSite`

### 7.2 第二轮：Resolve Semantics

目标：

- 根据 rule pack 解析 provider / injection / receiver 的语义绑定

典型结果：

- `beanA -> ImplA`
- `field a -> beanA`
- `field a -> ImplA`

### 7.3 第三步：Emit Graph Mutations

目标：

- 将解析结果转换为图边和属性

例如：

- `instance_of`
- `framework_injects`
- retarget 后的 `calls`

## 8. 梯度扩展模型

这是开源可用性的关键。修改成本必须随着定制深度梯度上升。

### 8.1 L1：只改 Rule Pack

适用场景：

- Spring Boot 和 Quarkus 这类同一 DI 元模型差异
- 调整 qualifier / primary / name 的优先级
- 调整哪些解析结果需要落图

开发者操作：

- 新增或覆盖 `rules-xxx.yml`
- 不改 Java 代码

这是默认扩展路径，也是最推荐的扩展层级。

### 8.2 L2：Rule Pack + Custom Functions

适用场景：

- 默认表达式能力不够
- 需要少量自定义提取或比较逻辑

开发者操作：

- 编写 `rules-xxx.yml`
- 注册少量 custom function
- 不改 pipeline 主流程

这一层不要求开发者理解全套内部抽象。

### 8.3 L3：新增 Semantic Pass

适用场景：

- 引入新的事实来源
- 现有元模型无法覆盖的新编程模型
- 接入数据流、事务、RPC 等新分析能力

开发者操作：

- 实现新的 semantic pass
- 产出新的 typed facts
- 复用现有 rule pack 和 mutation 机制

只有到这一层，才需要新增较重的代码扩展。

## 9. 推荐扩展点

为了避免过度设计，V1 对外优先暴露以下三个扩展点。

### 9.1 Rule Pack

默认扩展点。

rule pack 至少覆盖三类配置：

- `factMapping`
- `resolutionRules`
- `mutationRules`

示意结构：

```yaml
di:
  factMapping:
    providerAnnotations:
      - annotation: org.springframework.context.annotation.Bean
        providerNameFrom: methodName
        declaredTypeFrom: returnType
        actualTypeFrom: returnedInstantiationType
    injectionAnnotations:
      - annotation: org.springframework.beans.factory.annotation.Autowired
    qualifierAnnotations:
      - annotation: org.springframework.beans.factory.annotation.Qualifier
        valueFrom: value
    priorityAnnotations:
      - annotation: org.springframework.context.annotation.Primary
        priority: 100

  resolutionRules:
    order:
      - qualifier
      - explicitName
      - priority
      - uniqueCandidate

  mutationRules:
    bindingEdge: instance_of
    callRetargetEdge: calls
```

### 9.2 Custom Function Registry

次级扩展点。

适用场景：

- bean name 提取逻辑较特殊
- qualifier 比较存在轻度定制
- 规则表达式需要少量辅助函数

### 9.3 Semantic Pass Plugin

高级扩展点。

建议统一接口如下：

```java
public interface SemanticPass {
    String name();
    void collectFacts(AnalysisContext context, FactSink sink);
    void resolve(FactStore store, MutationSink sink);
}
```

普通用户不需要直接接触这一层。

## 10. DI 场景下的统一处理模型

对于 Spring Boot、Quarkus、CDI 这类共享 DI 元模型的框架，目标应当是：

`只切换 rule pack，不修改核心 DI 解析流程。`

### 10.1 第一轮统一收集

统一收集：

- `ProviderCandidate`
- `InjectionPoint`
- `CallSite`
- `TypeRelation`

### 10.2 第二轮统一解析

按规则执行：

- name 提取
- qualifier 匹配
- priority 排序
- unique candidate 回退

### 10.3 第三步统一落图

统一产出：

- provider / injection 绑定边
- retarget 后的调用边
- 可选的 framework 分类 edge

只要框架差异没有突破这套 DI 元模型，就不应该要求改核心代码。

---

## 11. DFG 的复用边界

本体系可以复用到数据流相关能力，但边界必须明确。

### 11.1 可复用部分

可复用的是：

- `DataFlowObservation` 的统一承载
- 基于规则的 summary 归纳
- 基于 mutation 的图边落库

例如：

- `returns_from`
- `writes_field`
- `reads_field`
- `passes_to`
- `flows_to`

### 11.2 不可替代部分

规则系统不替代以下能力：

- def-use 求解
- 路径敏感传播
- alias analysis
- interprocedural data flow
- fixpoint 计算

结论：

`DFG 引擎负责算事实，规则系统负责解释事实并产图。`

## 12. 二次开发者接入流程

### 12.1 场景 A：只适配 Quarkus

步骤：

1. 复制 `rules-spring.yml` 为 `rules-quarkus.yml`
2. 修改 provider / injection / qualifier / priority 的注解映射
3. 调整 resolution rules 顺序
4. 跑现有 DI 样例测试

不需要改 Java 核心代码。

### 12.2 场景 B：规则不够，需要少量定制

步骤：

1. 编写 `rules-xxx.yml`
2. 注册 1 到 2 个 custom function
3. 复用现有 collect / resolve / emit 流程

不需要新增新的 semantic pass。

### 12.3 场景 C：引入新语义能力

步骤：

1. 实现新的 semantic pass
2. 产出新的 typed facts
3. 编写对应 rule pack
4. 复用现有 mutation emitter

只有这种级别的需求，才需要理解更深层的内部设计。

---

## 13. 对 V1 的直接约束

基于本文档，V1 需要补齐或继续收敛的点如下：

1. DI 不再继续朝“Spring 专有 processor 巨石”演进
2. 规则系统优先服务于 rule pack + custom function 两层扩展
3. V1 文档必须明确：
   - 默认扩展方式是 rule pack
   - semantic pass 是高级扩展点
4. 与 DFG 相关的表述必须明确“复用解释框架，不复用分析求解”

---

## 14. 最终结论

开源可用的扩展体系，不应该要求所有用户都理解完整的内部抽象，而应该做到：

- 小需求：只改 rule pack
- 中需求：rule pack + 少量 custom functions
- 大需求：新增 semantic pass

也就是说：

`修改范围应随定制要求梯度上升，而不是一上来就把用户拖进完整内核。`

这才是适合 `maling-java-graph` 当前阶段的开源扩展设计。
