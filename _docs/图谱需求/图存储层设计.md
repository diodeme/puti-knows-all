# 图存储层设计

## 1. 文档目标

本文档用于定义 `maling-java-graph` 的图存储层抽象方案，解决当前实现对 Nebula 的强绑定问题，并为后续 `local_file`、`neo4j` 等后端接入预留统一边界。

本文档是 [`Java语义图谱V1开源重构任务书.md`](./Java语义图谱V1开源重构任务书.md) 在存储层上的补充设计，承接任务书中的 `code-graph-repository` 改造，但不改动任务书作为 V1 总纲的定位。

---

## 2. 核心结论

结论先行：

1. 这项改造值得做
2. 但不能理解成“把 `NebulaGraphClient` 改名成 repository 就完成了”
3. 真正要抽象的是四类能力：
   - 图写入
   - 图查询
   - schema 管理
   - 后端方言翻译
4. 所谓“DDL 通用”应理解为：
   - 通用的是逻辑 graph schema
   - 不是一份字面 DDL 直接跑 Nebula、Neo4j、本地文件

一句话概括：

`统一逻辑图模型，隔离后端实现差异，先做写入抽象，再做查询抽象。`

---

## 3. 当前问题

当前代码中，Nebula 绑定主要体现在三层：

### 3.1 分析写入链路

- `AbstractHandler` 直接创建 `NebulaGraphClient`
- `GraphContext` 直接携带 `NebulaGraphClient`
- analyzer processor 直接调用 `batchInsertNodes/batchInsertEdges`

结果：

- 底层后端无法通过 config 切换
- analyzer 与具体图库 SDK 耦合

### 3.2 查询链路

- `GraphQueryDao`
- documentation 模块中的 graph repository
- 测试与工具类

这些代码直接依赖：

- nGQL
- `ResultSet`
- `SHOW EDGES`
- `GET SUBGRAPH`
- `MATCH`

结果：

- 查询后端抽象尚未建立
- 即使写入侧解耦，读取侧仍然是 Nebula 强绑定

### 3.3 Schema 管理链路

- `EdgeSchemaRegistry` 保存逻辑 edge schema
- `NebulaSchemaManager` 直接把逻辑 schema 翻译为 Nebula DDL

这部分方向是对的，但现在仍缺少统一接口，导致 schema 管理能力无法自然挂到其他后端。

---

## 4. 设计目标

图存储层抽象需要同时满足以下目标：

1. analyzer/app 不直接依赖 Nebula SDK
2. 底层后端可通过 config 选择
3. `EdgeSchemaRegistry` 继续作为逻辑 schema 真相
4. Nebula 仍是默认生产实现
5. `local_file` 能作为调试、回归、离线导出后端
6. `neo4j` 有明确接入位，但不强行挤进当前 V1 主线

---

## 5. 非目标

本设计当前不追求以下目标：

- 一次性把所有查询能力都抽象完
- 一份字面 DDL 同时兼容所有后端
- 在 V1 内交付多个生产级图数据库实现
- 为本地文件后端补齐生产级多项目、多分支查询语义

---

## 6. 总体架构

建议把存储层拆成四个接口面。

### 6.1 写入接口：`GraphStorageRepository`

职责：

- 写入节点
- 写入边
- 批量写入
- 接收 analyzer 产出的图 mutation

约束：

- 不暴露 Nebula `ResultSet`
- 不暴露 nGQL
- analyzer 只依赖这层

### 6.2 查询接口：`GraphQueryRepository`

职责：

- 提供面向 server/documentation 的读取能力
- 返回项目自己的查询 DTO 或通用图协议对象

约束：

- service/dao 不直接消费后端原生返回对象
- `ResultSet` 不能越过 repository 泄漏到 service

说明：

- 这层应作为第二阶段改造
- 当前可先保留 Nebula 查询实现，但接口边界要预留

### 6.3 Schema 接口：`GraphSchemaManager`

职责：

- 根据 `EdgeSchemaRegistry` 校验和补齐逻辑 schema
- 管理后端侧的 schema 生效与缓存

典型实现：

- `NebulaSchemaManager`
- future `Neo4jSchemaManager`
- `LocalFileSchemaManager` 可为空实现

### 6.4 方言接口：`GraphDialect`

职责：

- 将逻辑 graph schema 翻译为后端的物理表达
- 将通用查询意图翻译为后端方言

说明：

- 这层不一定一开始就单独落类
- 但设计上必须存在，否则 repository 很快会重新长成 Nebula 巨石

---

## 7. 统一抽象边界

### 7.1 逻辑上统一的部分

以下内容应该跨后端统一：

- `Node`
- `Edge`
- `EdgeSchema`
- `EdgePropertySchema`
- `EdgeCategory`
- 图查询返回协议
- 业务层感知的查询意图

### 7.2 后端特化的部分

以下内容必须允许后端各自实现：

- 连接方式
- 物理 schema 语法
- 索引策略
- 查询方言
- 事务与批量写入策略
- 性能调优参数

---

## 8. “通用 DDL” 的正确理解

这是这次设计里最容易误判的点。

正确做法不是：

`一份 ddl.sql 同时适配 Nebula / Neo4j / local_file`

正确做法应该是：

`一份逻辑 schema + 多个后端 translator`

也就是：

1. `EdgeSchemaRegistry` 维护逻辑定义
2. Nebula 把它翻译成 `CREATE EDGE / ALTER EDGE`
3. Neo4j 把它翻译成约束、索引或属性约定
4. local_file 只需保证序列化结构一致，不必真的生成 DDL

所以，“DDL 通用”更准确的表述应当是：

`逻辑 schema 通用，物理 DDL/约束由后端适配。`

## 9. 推荐接口草案

### 9.1 写入接口

```java
public interface GraphStorageRepository extends AutoCloseable {
    void insertNode(Node node);
    void insertEdge(Edge edge);
    void batchInsertNodes(List<Node> nodes);
    void batchInsertEdges(List<Edge> edges);
}
```

### 9.2 查询接口

```java
public interface GraphQueryRepository {
    Optional<GraphNodeData> findNodeById(String nodeId);
    List<GraphNodeData> searchFunctionsByName(String methodName);
    GraphSubgraphData getSubgraph(String startId, int depth, GraphDirection direction);
}
```

### 9.3 Schema 接口

```java
public interface GraphSchemaManager {
    void ensureRegisteredSchemas();
    void ensureEdgeSchema(String edgeType, EdgeCategory category, Map<String, Object> properties);
}
```

### 9.4 工厂接口

```java
public final class GraphStorageRepositoryFactory {
    public static GraphStorageRepository create(AppConfig config) { ... }
}
```

## 10. 推荐配置模型

建议统一引入：

```properties
graph.storage.type=nebula
```

可选值建议：

- `nebula`
- `local_file`（兼容 `local-file`）
- `neo4j`

扩展说明：

- `nebula`：默认生产实现
- `local_file`：本地调试、导出、回归验证
- `neo4j`：预留值，未实现前显式报错，不要静默回退

V1 约束：

- 不单独增加 `graph.storage.path`
- `local_file` 落盘目录由 `project.root_path` 自动推导，固定到 `.maling/graph-storage/<projectId>/<branch>/`

## 11. 分阶段实施建议

### 11.1 第一阶段：写入侧解耦

目标：

- analyzer/app 不再直接依赖 `NebulaGraphClient`
- 引入 `GraphStorageRepository`
- 接入 `GraphStorageRepositoryFactory`
- 提供 `NebulaGraphStorageRepository`
- 提供 `LocalFileGraphStorageRepository`

这一阶段完成后，至少能做到：

- 同样的分析结果可以落 Nebula
- 也可以直接导出到本地文件

### 11.2 第二阶段：查询侧解耦

目标：

- 引入 `GraphQueryRepository`
- server/documentation 不再直接持有 `ResultSet`
- 把后端 native result 解析收口到 repository 内

这一阶段才是真正让 `neo4j` 具备可接入性的关键。

### 11.3 第三阶段：后端扩展

目标：

- 按需补 `Neo4jGraphStorageRepository`
- 按需补 `Neo4jGraphQueryRepository`
- 引入 backend capability 说明

---

## 12. 后端能力分层建议

建议把后端支持程度分成三档，避免“接了一个名字，就算支持一个后端”。

### L1：写入后端

能力：

- 能落节点
- 能落边
- 能承载逻辑 schema

示例：

- `local_file`

### L2：可查询后端

能力：

- 支持核心查询协议
- 能返回通用图协议数据

示例：

- `nebula`

### L3：生产级后端

能力：

- 写入
- 查询
- schema 管理
- 基础性能保障
- 集成测试闭环

示例：

- 当前默认目标仍是 `nebula`

---

## 13. 与当前 V1 的关系

这个设计和当前 V1 任务书并不冲突，但需要明确边界：

1. V1 总纲仍以 Nebula 为默认落地对象
2. 存储抽象可以进入当前代码基线
3. `local_file` 可以作为 V1 内的辅助实现
4. `neo4j` 建议放到 V1.x
5. 查询抽象如果本轮不做完，必须明确写成“阶段二”

换句话说：

`V1 可以做存储抽象，但不应把自己升级成“多图数据库平台首版”。`

---

## 14. 建议的最小落地范围

如果只做一轮最小改造，建议范围是：

1. 引入 `GraphStorageRepository`
2. `AbstractHandler`、`GraphContext`、analyzer processor 改依赖写入接口
3. 保留 `NebulaSchemaManager`
4. 提供 `local_file` 写入与基础查询实现
5. 任务书在 repository 章节引用本文档

不要在这一轮同时强推：

- server 全量查询抽象
- documentation 全量查询抽象
- Neo4j 正式接入

---

## 15. 最终建议

我的建议是：

- 方向可行，而且应该做
- 但要按“写入先行、查询随后、后端逐步接入”的顺序推进
- 任务书保持总纲，不在总纲里展开全部存储细节
- 详细设计单独落在本文档中维护

最终可以把目标表述为：

`以统一逻辑图 schema 为核心，建立可插拔图存储层；V1 默认 Nebula，支持 local_file，Neo4j 延后到 V1.x。`
